# B-race Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a runner add tune-up races (B-races) to a race plan, get a rule-based opinion and a safer option, have the
plan taper and recover around the race, and get a debrief afterwards.

**Architecture:** A pure rules module (`services/b_race.py`) decides the verdict, taper and recovery. A `plan_races` table
stores the races. A code guard in plan post-processing pins the race day, the taper and the recovery window whatever the
model writes. Adding or cancelling a race reuses the adapt-week job for weeks already generated. The model only words
the opinion and the debrief, grounded on facts, with rule-written fallbacks.

**Tech Stack:** FastAPI + SQLAlchemy Core (`text()`), Alembic, pytest; Next.js 16 + vitest; SwiftUI + Swift Testing.

**Spec:** `docs/superpowers/specs/2026-10-26-b-race-design.md` (mockups: https://claude.ai/artifact/XHSuX1qZMixkVMDZHZzJzj)

## Global Constraints

- Verdict levels, exactly: `good`, `conditions`, `risky`, `not_recommended`. The model never sets a level, a taper or a recovery length.
- `not_recommended` when `days_before_a < 14`. Such a race is planned as training effort: no own mini-taper, A-race taper and race week untouched.
- Taper / recovery by effort-km (km + gain_m/100, `athlete_tier.effort_km` rule): ≤21 → 2/3 days; 22–42 → 3/5; 43–70 → 3/7; >70 → 4/10. Training effort: taper `max(1, taper-1)`, recovery `ceil(recovery/2)`. A race kept against `risky`: recovery +2 days.
- Taper day: easy, ≤ 50% of that week's median easy-session minutes, no hard session; last taper day may have 2–3 strides. Recovery window: Zone 1 only, ≤ 60 min, no hard session, no long run.
- B-races only on plans with `goal_type` in (`finish`, `time`, `optimal`); date strictly after the plan start Monday and before the A-race date; at most 3 with `status='planned'` per plan.
- The runner always has the final say: every level can be kept (`not_recommended` only as training effort).
- Every schema change goes in BOTH `db.py:init_db()` and an Alembic migration (`db-migration` skill). New table creation in `init_db` comes after `plans`, `workouts` and `activities`.
- Model text: every number must appear in the facts (`coach_nudge.grounded`); otherwise use the rule-written en/vi text. Prompts are Langfuse text prompts via `observability.load_prompt(name, FALLBACK)`.
- vi copy follows the `uphill-ai-vietnamese-copy` skill. UI changes need screenshots (`ui-screenshot-evidence`).
- Repo is public: never commit secrets. Integration tests TRUNCATE: scratch DB only. Paid model checks only with the owner's OK.

## Review Focus

1. A B-race whose date falls in a week that is already partly logged: the rebuild must keep logged sessions and only replace future rows (test in Task 7).
2. Two B-races in consecutive weeks: the second race's taper days overlap the first race's recovery window. Recovery wins: the overlap stays Zone 1 and no day gets two rules (test in Task 5).
3. The A-race date moves (plan edited) after a B-race was added: the B-race now sits inside 14 days or after the A-race. The list endpoint must re-assess on read rather than show a stale level (test in Task 4).
4. A race with no distance (not in the race list, runner typed only a name): assess must refuse with a clear 422, not crash or guess (test in Task 4).
5. A synced activity on race day that is clearly not the race (a 5 km shakeout before a 42K): it must not be linked as the result (distance within 15% rule; test in Task 10).

- [ ] **Step 3: Implement the module**

Rules in `assess`, first match wins:
- `days_before_a = (facts.a_date - race.race_date).days`; `load_ratio = race_effort_km / longest_recent_km` (None when unknown → skip load rules); `size_ratio = race_effort_km / race_effort_km(A)`.
- `not_recommended`: `days_before_a < 14`.
- `risky`: recovery window (`race_date+1 … race_date+recovery_days`) reaches the first Taper week or a Peak week (phases from `PlanGenerator.phase_for_week(w, total_weeks)`, week via `week_and_day`) → `overlaps_taper` / `overlaps_peak`; or another planned race at race effort within 21 days (28 if either effort-km ≥ 42) → `stacked`; or race effort and `load_ratio > 1.5` → `longer_than_trained`.
- `conditions`: race effort and `1.2 < load_ratio ≤ 1.5` (`longer_than_trained`); or race effort and `14 ≤ days_before_a < 28`; or phase `Base` and `size_ratio > 0.6` (`base_phase`).
- Training effort skips the `load_ratio` and `days_before_a` race-effort rules.
- `suggestion` is set when the level is not `good`: candidates in order — each `options_km` shorter than the race, longest first, at `race`; the same distance at `training`; shorter options, longest first, at `training`. A shorter option's climb is the race's climb scaled by the distance ratio. First candidate whose `assess` is `good` wins; none → the shortest available at `training`.

`enforce` for each race whose week is in `workouts`:
1. Ensure one row `type="Race"`, `title=race_name`, `plan_race_id`, `duration_minutes` = predicted mid (else 6 min/effort-km), `is_priority=True`, on its day; drop every other row that day.
2. Remove a remaining `Long Run` in the race week (the race replaces it).
3. Taper days (the `taper_days` days before the race): drop hard sessions (`plan_lint.is_hard`); cap each to 50% of the week's median easy minutes; add `"+ 3 × 20 s strides"` to the last taper day's description. Skipped for `not_recommended`/training effort beyond 1 day.
4. Recovery window (`recovery_days` after, crossing into the next week): each session becomes Zone 1, ≤ 60 min; drop hard sessions and long runs (to `Rest` rows, `_make_rest` style).
5. Never touch weeks whose phase is `Taper` or `Race Week` for the A-race; overlapping rules: recovery wins over taper (Review Focus 2).

Also produces `cost(race: dict, verdict: dict, workouts: list[dict], plan_monday: date) -> dict` — a dry run of `enforce` on a deep copy of the plan's current workouts: `{"changed": [{"week", "day", "title_before", "title_after", "minutes_before", "minutes_after"}], "peak_week_minutes": {"before", "after"} | None}`. From this task on, Task 4's `assess` and create responses include it as `verdict["cost"]` (`null` before) (the risky screen's "what it would cost" list).
