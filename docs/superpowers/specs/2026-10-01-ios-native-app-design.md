# Native iOS app: design and roadmap

Date: 2026-10-01
Status: approved roadmap; Phases 0 and 1 have detailed plans, Phases 2-7 get theirs when they start.

## Why

The Capacitor app got Uphill AI onto phones quickly, but stakeholders find the UI complex and it feels like a website. The web revamp (Phase 1 app shell, branch `claude/ui-ux-revamp-review-22c6db`) settled a simpler information architecture: Plan / Coach / Me tabs, a swipeable plan summary, collapsed rest days, a Today label and an explicit Priority marker. We build a native SwiftUI app on that information architecture instead of porting the old screens.

A native app also unlocks what the web view cannot do well:

- **Apple Watch without Garmin or Strava.** The Garmin developer programme is closed and Strava's API terms ban AI use. WorkoutKit pushes structured workouts straight to Apple Watch, and HealthKit reads finished runs back.
- **Native feel.** Real sheets, paging, haptics, a Today widget, Live Activities.

## Decisions

| Topic | Decision |
|---|---|
| Stack | SwiftUI, Swift 6 language mode (strict concurrency), `@Observable` |
| Minimum OS | iOS 18.0, iPhone only |
| v1 scope | Full parity with the web app, including coach-side features (last phase before 1.0) |
| Repo | This monorepo, directory `ios-native/` |
| Project file | Generated by XcodeGen from `ios-native/project.yml`; `*.xcodeproj` is git-ignored |
| Bundle ID | `ai.uphill.app` (same as the Capacitor app; the native build replaces it in place on TestFlight) |
| Offline | Read-only cache of profile, active plan and workouts (SwiftData). Writes and chat need a connection |
| Languages | English first; Vietnamese strings via a String Catalog before 1.0 (Phase 7) |
| Web | Finish web Phase 1 behind its flag, merge, then freeze the web app except fixes. Web stays the Android path |

## Architecture

```
ios-native/
  project.yml                 XcodeGen spec (app + test targets)
  Config/                     Debug/Release xcconfig, Info.plist values
  UphillAI/
    App/                      @main, root TabView, environment wiring
    Core/
      Networking/             APIClient, Endpoint, APIError, SSE reader (Phase 3)
      Auth/                   SessionStore, KeychainStore, sign-in providers
      Models/                 Codable DTOs mirroring backend JSON (snake_case)
      Persistence/            SwiftData cache models and CacheStore
      Environment/            AppEnvironment (prod / staging / local base URLs)
    DesignSystem/             Colors, typography, spacing, radii, shared components
    Features/
      Auth/  Plan/  Me/       Phase 0-1
      Onboarding/ Chat/ Health/ Tools/ Knowledge/ CoachDashboard/   later phases
  UphillAITests/              Swift Testing unit tests + JSON fixtures
  UphillAIUITests/            XCUITest flows
```

Rules:

- **Features depend on Core and DesignSystem only**, never on each other. Cross-feature navigation goes through the root `AppRouter`.
- **One `APIClient`**, `async throws`, Bearer token from `SessionStore`. A 401 clears the session and returns the user to sign-in.
- **DTOs are hand-written `Codable` structs.** FastAPI has no `response_model` on any endpoint, so OpenAPI codegen would produce untyped responses. Every DTO is decoded in a test against a JSON fixture recorded from the real local backend (`UphillAITests/Fixtures/*.json`), so a backend shape change breaks a test instead of the app. Unknown keys are ignored; fields the backend may omit are optionals.
- **View models are `@Observable @MainActor` classes**, one per screen, taking protocols (`PlanServicing`, `AuthServicing`) so tests inject fakes.
- **Environment switch**: Debug builds offer prod / staging / local (`http://localhost:8000`) in a hidden developer menu (long-press the version label in Me). Release builds are pinned to prod.

### Design system

Tokens come from `DESIGN.md` and the web Phase 1 shell: emerald accent `#19ce8b`, accent ink `#08764f`, button ink `#063e2b`, ink `#172b26`, secondary `#455c52`, muted `#5d7167`, line `#dce5df`, radii 6/8/10/12/16, spacing 8/12/16/20/24/28/32. Typography uses the system font (SF Pro) with Dynamic Type; we do not bundle Plus Jakarta Sans in v1. The app is light-only until Phase 7 decides on dark mode. No mountain video; native screens use the opaque `landing-surface` `#f8faf8` background.

Motion and feel follow the `apple-design` skill (`.claude/skills/apple-design/SKILL.md`), translated to SwiftUI:

- Default animation is a critically damped spring: `.spring(response: 0.35, dampingFraction: 1.0)`. Bounce (`dampingFraction: 0.8`) only after a gesture that carried momentum (a flick, a drag release).
- Prefer system components (`TabView`, `.sheet` with detents, `ScrollView` paging, `Menu`): they already track the finger, carry velocity and can be interrupted. Write a custom gesture only where no system component fits.
- Haptics through `.sensoryFeedback` on the causal event only: `.success` when a workout is marked done, `.error` on a failed save, `.selection` when the week changes. Nothing else buzzes.
- Respect `accessibilityReduceMotion` (cross-fade instead of slide/spring) and Dynamic Type (no fixed-height text containers).
- Press feedback is instant: buttons use a `ButtonStyle` that scales to 0.97 on press.

### Backend changes the app needs

| Change | Phase |
|---|---|
| `POST /api/auth/apple` (verify Apple identity token against Apple's JWKS, audience `ai.uphill.app`) | 0 |
| `/api/auth/google` checks the token's `aud` against an allow-list (`GOOGLE_CLIENT_IDS`: web + iOS client IDs). Today it accepts any Google ID token | 0 |
| HealthKit run import endpoint (reuses the activity matching pipeline) | 4 |
| APNs device registration + push sender | 4 |
| `DELETE /api/auth/account` (App Store guideline 5.1.1(v): apps that allow sign-up must offer in-app account deletion) plus a Delete account row in Me | 7, before App Store submission |

Each backend change follows the repo rules: dual schema for any table change, integration tests only against a scratch database.

## Roadmap

Each phase ends with an internal TestFlight build. A phase is done when its plan's tasks pass review and the Simulator screenshots are attached to the PR.

| # | Phase | Contents | TestFlight milestone |
|---|---|---|---|
| W | Finish web Phase 1 | Re-seed local data, re-verify commit `0d3089a`, merge with flag on in staging | Web reference design |
| 0 | Foundations | XcodeGen project, design tokens, APIClient, Keychain session, email + Google + Apple sign-in, environment switch, CI build/test job, release script | Sign in, see your profile |
| 1 | Plan core | Plan tab: summary carousel (volume, race, this week, phase), week list, collapsed rest days, Today/Tomorrow labels, Priority marker, workout detail, mark done/missed + RPE + notes, move a workout, Manage sheet (load recent plan), offline cache, Me tab (profile, sign out) | Daily-use plan viewer |
| 2 | Onboarding and plan generation | Onboarding wizard, generate plan with job polling and a progress screen, plan settings, start new plan, next block, adapt week, weekly review, Goal pill and goal assessment | New users can start in the app |
| 3 | Coach chat | SSE streaming, proposals apply/discard, sources, daily limits, retries | Coach Uphill in the app |
| 4 | Watch and health | WorkoutKit push of scheduled workouts, HealthKit import of finished runs, matched activities on the plan, local reminders, APNs, Today widget | Main native advantage |
| 5 | Tools and knowledge | Pace Strategy, Gear, Nutrition, Goal Determiner, Knowledge Hub, race history, COROS/EvoLab connections, GPX/FIT import, calendar export (EventKit) | Athlete parity with web |
| 6 | Coach side | Roster, invites, athlete plan view/edit, approve/remove workouts, Priority toggle, notes | Coaches move to the app |
| 7 | Release | Parity audit vs web, accessibility audit, Vietnamese strings, App Store listing, privacy labels, HealthKit review notes, retire Capacitor iOS | App Store 1.0 |

Order rationale: Plan core first because it is what athletes open daily. Chat before Watch because chat only needs an existing endpoint, while Watch/Health need new backend endpoints and Apple entitlements review.

## Testing

- **Unit (Swift Testing):** DTO decoding against fixtures, view-model logic with fake services, date/week maths shared with the web (`planDate`, `planSummary` equivalents ported with the same test cases).
- **UI (XCUITest):** a few end-to-end flows per phase against the local backend with a seeded user. Never run backend integration tests against `uphill_ai`; they truncate every table.
- **Screenshots:** every UI change is shown with an iOS Simulator screenshot (iPhone 16, iOS 18) before it is called done.
- **CI:** a GitHub Actions `macos-15` job runs `xcodegen generate` then `xcodebuild test` on changes under `ios-native/`.

## Out of scope for v1

iPad layout, Apple Watch companion app (WorkoutKit covers the Watch need), Android native, dark mode (decided in Phase 7), Facebook login on iOS.

## Risks

- **App Review:** replacing a web-view app with a native one under the same bundle ID is fine; HealthKit requires a clear privacy policy and in-app explanation of use.
- **Sign in with Apple** is mandatory once Google sign-in is offered (App Store guideline 4.8).
- **Backend drift:** no response models on the backend. The fixture tests are the guard; re-record fixtures when an endpoint changes.
- **Plan length:** full parity is long. Each phase ships to TestFlight so stakeholders see progress.
